# Тест-план
## для модульного и нагрузочного тестирования "Candy Delivery API"

### 1. Введение
**1.1. Цель:** Обеспечить контроль качества backend-части системы, проверить корректность бизнес-логики, валидации данных и устойчивость API к нагрузке.

**1.2. Объект тестирования:** REST API веб-сервис на фреймворке FastAPI (эндпоинты `/api/login`, `/couriers`, `/orders`, `/orders/assign`, `/orders/complete`).

### 2. Стратегия тестирования
- **Модульное (интеграционное) тестирование API:** Автоматизированная проверка HTTP-методов с использованием библиотеки `pytest` и `requests`. Проверка как позитивных сценариев (HTTP 200/201), так и негативных (HTTP 400, 401, 404).
- **Нагрузочное тестирование:** Имитация множественных параллельных запросов к критическим эндпоинтам для оценки времени отклика и стабильности соединения.

### 3. План модульного тестирования (API)
Тесты расположены в директории `backend/tests/`.

| № | Тестируемый эндпоинт | Сценарий | Ожидаемый результат |
|---|----------------------|----------|---------------------|
| 1 | `POST /api/login` | Успешный вход (admin/courier) | Статус 200, наличие `access_token` и `role` |
| 2 | `POST /api/login` | Неверный пароль или пользователь | Статус 401, сообщение об ошибке |
| 3 | `POST /couriers` | Импорт валидных данных курьеров | Статус 201, возврат списка ID |
| 4 | `POST /couriers` | Импорт невалидных данных (отрицательный ID, неверный тип) | Статус 400, описание ошибки валидации |
| 5 | `GET /couriers/{id}` | Получение существующего курьера | Статус 200, корректные поля (включая рейтинг и заработок) |
| 6 | `GET /couriers/{id}` | Запрос несуществующего курьера | Статус 404 |
| 7 | `PATCH /couriers/{id}` | Обновление данных курьера | Статус 200, обновленные данные, сброс неактуальных заказов |
| 8 | `POST /orders` | Импорт валидных заказов | Статус 201, возврат списка ID |
| 9 | `POST /orders/assign` | Назначение заказов доступному курьеру | Статус 200, список назначенных ID и `assign_time` |
| 10| `POST /orders/complete` | Завершение назначенного заказа | Статус 200, изменение статуса на "completed" |
| 11| `POST /orders/complete` | Попытка завершить чужой или несуществующий заказ | Статус 400 |

### 4. План нагрузочного тестирования
**4.1. Инструмент:** Скрипт на Python с использованием библиотеки `requests` и `concurrent.futures`.

**4.2. Сценарий:**
1. Авторизация под администратором (получение токена).
2. Циклическая отправка 1000 GET-запросов к `/couriers` и `/orders` в 10 параллельных потоков.

**4.3. Измеряемые метрики:**
- Среднее время отклика (Response Time).
- Процент успешных запросов (Success Rate, цель: 100%).
- Отсутствие утечек памяти или блокировок БД (Deadlocks).

### 5. Критерии начала и окончания тестирования
- **Начало:** Реализованы все эндпоинты API, настроена тестовая база данных PostgreSQL, файл `.env` сконфигурирован.
- **Окончание:** 100% тестов из набора `pytest` проходят успешно (статус PASSED), критические баги, выявленные при тестировании, исправлены.
